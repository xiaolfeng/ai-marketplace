# design-er · 设计模式（含 `draft → rfc → adr` 演进）

公共约定：[../_shared/conventions.md](../_shared/conventions.md) ·
Scope 词表：[../_shared/scope-manage.md](../_shared/scope-manage.md) ·
流转与状态：[../_shared/lifecycle.md](../_shared/lifecycle.md) ·
语言纪律：[../_shared/writing-style.md](../_shared/writing-style.md)

## 阶段定位：单文件原位演进

`design` 不再把「提案（rfc）」和「定稿（adr）」拆去别的目录，而是在同一篇 `docs/engineering/design/NNNN-<scope>-<title>.md` 内按三个过程阶段原位演进：

| 阶段状态              | 定位                     | 写作要求                                                                                                                                             |
| --------------------- | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`draft`**（起草）   | 初步构思与方案探索       | 新建默认状态。勾勒目标与边界、初步工作方式；允许保留并列思路与待验证问题                                                                             |
| **`rfc`**（提案描述） | 面向评审人的收敛方案     | 方案已收敛为单一主推方向。完整写清**工作方式、数据与接口、异常与兼容、备选与不做什么（遵循最强反驳原则）、验证与待确认项**                           |
| **`adr`**（定稿约束） | 拍板冻结的架构与设计契约 | 经用户明确确认后升级。**清零阻塞性「待确认」项**，固化设计边界、物理极限与重评退出条件；进入 `adr` 后正文锁定，后续推翻须新建文档并互标 `superseded` |

（另支持终态 `rejected` 评审否决、`superseded` 被新设计取代。）

## 操作流程

复制此清单并随做随勾：

```
设计稿进度：
- [ ] 1. 判定本次动作：新建设计（默认 draft，或方案已收敛直接写 rfc 内容但状态仍从 draft 起步） vs 推进既有设计阶段（draft → rfc → adr）
- [ ] 2. 核对承接的 research / spec 及仓库真实代码，界定涉及与不涉及的模块边界
- [ ] 3. 按统一主骨架成文或演进：补齐职责、数据接口、异常兼容、备选与不做什么、可执行验证
- [ ] 4. 对照 writing-style.md 检查技术真实性（反稻草人拉踩、工作树现状与规划分流、物理失效边界与重评条件）
- [ ] 5. 新建时只扫 docs/engineering/design/ 取最大编号 +1，命名 NNNN-<scope>-<title>.md 落盘；演进时原文件原位更新
- [ ] 6. 同步登记或更新 docs/README.md 的「设计模式（design）」分表，回报路径、当前阶段与待确认项
```

## 文档骨架（统一主骨架，按阶段收敛）

```markdown
# 标题

> 状态：draft | rfc | adr · 日期：YYYY-MM-DD · Scope：<scope>
> 承接：[调研/前序文档标题](../research/NNNN-scope-title.md)（如有）

## 目标与边界

要解决的具体工程问题、实现要满足的行为，以及本次明确涉及与**不做什么**（每条排除项带一句原因）。
涉及自研或核心改造时，表格化分流「当前工作树现状」与「本次/后续规划」。

## 工作方式

从入口到输出的调用顺序、组件职责和关键状态变化；标出读写与并发边界。
（`draft` 阶段可保留并列设想；进入 `rfc` / `adr` 必须收敛为唯一可执行链路。）

## 数据与接口

输入、输出、格式、校验、持久化与兼容要求；给出必要的字段表或函数签名。

## 异常与兼容

失败时的表现、超时/强杀/级联异常等物理边界、重试或回退条件，以及已有调用方如何继续工作。禁止承诺「绝对安全」。

## 备选与取舍

| 备选方案 | 否决原因（须对应目标与边界）                               |
| -------- | ---------------------------------------------------------- |
| 方案 A   | 具体权衡原因（遵循最强反驳原则，禁止立稻草人拉踩开源方案） |

涉及自建机制时，必须在此写明**重新评估与退出条件**（出现何种具体指标时推翻自建）。

## 验证

逐项列出可运行的检查命令、关键边界用例及其预期结果。

## 待确认

- `draft` / `rfc` 阶段：列出仍需决策的事项及是否阻塞实现；
- `adr` 阶段：必须全部达成决议并清零（写「无（已于 YYYY-MM-DD 定稿冻结）」）。
```

## 阶段纪律

1. **`adr` 只能由人确认升级**：即便用户说「写个详细设计」，新建落盘也从 `draft`（或经用户明确要求进入 `rfc` 评审态）起步，未获明确拍板不得标为 `adr`；
2. **`adr` 正文不可直接篡改**：定稿后若需求或架构推翻，新建 `NNNN+1` 设计稿，旧文状态改 `superseded` 并双向链接；
3. **跨模式分流**：若设计中包含需要跨模块长期遵守的通用标准/红线，抽入 `spec-er`；若涉及多期推进、灰度迁移与任务拆解，交由 `plan-er` 落盘至 `docs/plan/`。
