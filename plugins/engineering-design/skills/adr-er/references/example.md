# ADR 好坏对照

同一个主题（「市场清单单一源定稿」）的两个版本。坏例的问题不是错，
而是**没人能照着它执行**——定稿的价值恰恰在可执行。

## 坏例

```markdown
## ADR：关于市场清单架构的最优决策

### 背景
经过多轮深入讨论与充分调研，团队对清单架构形成了高度一致的认知。

### 决定
原则上采用 Claude 格式作为主要载体，同时尽量保持对其他平台的
兼容性与扩展性，在实践中不断优化和完善相关流程。

### 意义
这一决策具有里程碑意义，为插件库的长远发展奠定了坚实基础，
将有力推动生态建设迈上新台阶。
```

**输在哪**：

1. 「原则上」「尽量」——决定条款里最致命的两个词，等于没决定；
2. 「形成高度一致认知」——过程叙事，不是契约内容；
3. 「里程碑」「坚实基础」——庆祝词。ADR 不是新闻稿；
4. 没有任何一条能被单独引用执行：什么叫「主要载体」？「保持兼容」具体指什么？
5. 缺否决项——三个月后有人提议「双清单手动同步」时，没有文档拦得住他。

## 好例

```markdown
> 状态：proposed · 承接 [0005](../rfc/0005-marketplace-single-source.md)

## 背景
各客户端清单格式不通用；多份手写索引已经出现过一次漏改导致的更新丢失。

## 决定
1. **`.claude-plugin/marketplace.json` 是唯一允许手写的清单。**
   禁止直接修改 `dist/` 下任何导出产物——导出物由脚本从唯一源生成。
   手写 Cursor 清单的 PR 一律不合并：两份手工索引必然漂移。
2. **新增平台适配 = 新增导出规则，不改插件本身。**
   插件目录结构保持 Agent Plugins 1.0 兼容；
   平台差异只体现在导出器的映射逻辑里。
   例外：平台要求的字段若影响插件本体（如 manifest 必填项），
   先在本文件的后续条款中追加约定再实施。

## 后果
- 得到：改一处全平台生效；清单冲突类 bug 只可能出现在导出器；
- 失去：新平台上线前要先写导出规则，不能直接手补清单应急；
- 违反时暴露方式：某平台清单与其他平台不一致 → 说明有人绕过了导出器。

## 否决项
- **双清单人工同步**：靠人记住两处版本号，第一次赶工就会漏——本 ADR 的动机正是这次漏改；
- **JSON Schema 工具链双向同步**：为 4 个插件引入冲突合并机制，收益不成比例。
  注意：单向导出不受此禁令限制，未来插件规模增长可重新评估。
```

**好在哪**：

1. 每条决定都有精确禁令和例外边界，单独贴出去就能执行；
2. 「违反时暴露方式」让半年后的维护者知道该查哪里；
3. 否决项拦住了两个可预见的回头路，且排除了容易误伤的合法场景（单向导出）;
4. 全文没有一个形容词是装饰性的。
