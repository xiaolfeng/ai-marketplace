# 草案好坏对照

同一个主题（「市场清单架构」）的两个版本。坏例的问题不是写得差，
而是**它根本不是草案**——困惑没写出来，结论倒是先定了。

## 坏例

```markdown
## 问题
经过初步分析，我认为插件市场清单应该采用统一格式管理，
这个方向基本是明确的，后续按此推进即可。

## 初步想法
采用 Claude marketplace 格式。这是最优方案，无需过多犹豫。

## 缺什么
暂无明显缺口。

## 下一步
直接开始实施。
```

**输在哪**：

1. 「基本是明确的」「无需过多犹豫」——草案阶段出现结论词，判断越界了；
2. 困惑是什么没说——三个月后回看，不知道当时到底在纠结什么；
3. 「暂无明显缺口」等于没思考；并列想法只剩一条，说明自我审查过了头；
4. 下一步跳过 research / rfc 直接实施——流转链条在这里断了。

## 好例

```markdown
> 状态：open · 记录日期：YYYY-MM-DD

## 问题
五个客户端各有清单格式，每接入一个平台就要多手工维护一份索引，
上次漏改导致用户收不到更新——但我还没想好该统一到什么程度。

## 初步想法
- 全部收敛到 Claude 格式，其他平台脚本导出？
- 或者反过来，以约束最严的格式为基准？
- 要不要干脆自建 registry 服务？
- 也许只需要一个校验脚本防漏改，不急着统一？

## 缺什么
- 各客户端对清单字段的最小要求对照表；
- 自建 registry 的维护成本量级；
- 「漏改」事故的具体成因——是流程问题还是格式问题。

## 下一步
缺证据 → 转 research。
```

**好在哪**：

1. 困惑具体到「统一到什么程度」，一眼看出卡点；
2. 四条想法互相矛盾也照单全收——草案的功能是防遗忘，不是下结论；
3. 缺口三条条条能变成调研任务，research 拿去就能开工；
4. 全文十分钟内可写完，没有一句装成熟。
