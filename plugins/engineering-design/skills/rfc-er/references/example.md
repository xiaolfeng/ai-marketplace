# RFC 好坏对照

同一个主题（「市场清单单一源」）的两个版本。坏例是真实 AI 产出里最常见的失败方式：
不是写错了，而是**写了太多没人需要的东西**。

## 坏例

```markdown
## RFC：关于插件市场清单架构方案的深入探讨

### 一、背景介绍
在 AI 插件生态蓬勃发展的今天，插件市场的清单管理扮演着举足轻重的角色。
为了让大家更好地理解本方案，我们先来回顾一下插件市场的发展历程……

### 二、现状分析
（此处用 40 行复述了 research 文档里已有的内容……）

### 三、方案设计
经过深思熟虑，我们建议采用 Claude marketplace 格式作为核心载体。
该格式具有诸多优势：标准化程度高、社区认可度好、扩展性强……
（连续 12 个形容词，没有一条具体条款。）

### 四、实施计划
第一阶段：完成技术选型论证；第二阶段：开展详细设计；
第三阶段：推进落地实施并持续优化迭代。

### 五、总结与展望
综上所述，本方案兼顾了前瞻性与可行性，相信能够为插件库的
长远发展奠定坚实基础。
```

**输在哪**：

1. 「蓬勃发展」「举足轻重」「深思熟虑」——零信息量的装饰词；
2. 「现状分析」整章在复述 research 已有的内容——链接过去即可，评审人早就读过；
3. 方案只有形容词没有条款——评审人无法回答「到底采用什么」；
4. 「实施计划」是三句正确的废话，没有任何可执行动作；
5. 没有「不做什么」、没有「备选」、没有「待定」——评审人最想看的三个部分全部缺席；
6. 五个章节，真正有信息量的不到十行。

## 好例

```markdown
> 状态：draft · 承接 [0001](../research/0001-plugin-standards.md)

## 问题
各客户端市场清单格式不通用，同一批插件要维护多份索引，
漏改一处用户就收不到更新。

## 方案
1. **只手写一份 `.claude-plugin/marketplace.json` 作为唯一事实源。**
   其他平台的清单一律由脚本导出——手改 Cursor 清单的 PR 一律拒绝，
   否则两份清单必然漂移。
2. **导出器读源清单生成 `dist/cursor/`。** 字段一一映射，
   不做任何智能转换——转换逻辑越聪明，排查越痛苦。

## 不做什么
- 不做自建 registry API——当前 4 个插件撑不起一个服务；
- 不适配 Gemini CLI——其生态正在换代，等稳定再接。

## 备选

| 方案 | 否决原因 |
| --- | --- |
| 每平台手写一份清单 | 违反方案第 1 条，漂移只是时间问题 |
| 用 JSON Schema 工具链自动双向同步 | 双向同步需要解决冲突合并，复杂度远超收益 |

## 待定
Cursor 官方市场提交流程是否接受 dist 导出物——不阻塞 draft 评审。
```

**好在哪**：

1. 问题两句讲完，没有发展史；
2. 方案两条都有具体动作和拒绝条件，评审人能直接说同意或反对；
3. 「不做什么」堵住了两个必然被问到的方向；
4. 备选表每条否决原因都对得上方案条款；
5. 全文不到一屏，但决策所需的全部信息都在。
