# RFC 好坏对照

同一个主题（「市场清单单一源」）的两个版本。坏例是真实 AI 产出里最常见的失败方式：
不是写错了，而是**写了太多没人需要的东西**。

## 坏例

```markdown
## RFC：关于插件市场清单架构方案的深入探讨

### 一、背景介绍

在 AI 插件生态蓬勃发展的今天，插件市场的清单管理扮演着举足轻重的角色。
为了让大家更好地理解本方案，我们先来回顾一下插件市场的发展历程……

### 二、现状分析

（此处用 40 行复述了 research 文档里已有的内容……）

### 三、方案设计

经过深思熟虑，我们建议采用 Claude marketplace 格式作为核心载体。
该格式具有诸多优势：标准化程度高、社区认可度好、扩展性强……
（连续 12 个形容词，没有一条具体条款。）

### 四、实施计划

第一阶段：完成技术选型论证；第二阶段：开展详细设计；
第三阶段：推进落地实施并持续优化迭代。

### 五、总结与展望

综上所述，本方案兼顾了前瞻性与可行性，相信能够为插件库的
长远发展奠定坚实基础。
```

**输在哪**：

1. 「蓬勃发展」「举足轻重」「深思熟虑」——零信息量的装饰词；
2. 「现状分析」整章在复述 research 已有的内容——链接过去即可，评审人早就读过；
3. 方案只有形容词没有条款——评审人无法回答「到底采用什么」；
4. 「实施计划」是三句正确的废话，没有任何可执行动作；
5. 没有「不做什么」、没有「备选」、没有「待定」——评审人最想看的三个部分全部缺席；
6. 五个章节，真正有信息量的不到十行。

## 好例

```markdown
> 状态：draft · 承接 [0001](../research/0001-plugin-standards.md)

## 问题

各客户端市场清单格式不通用，同一批插件要维护多份索引，
漏改一处用户就收不到更新。

## 方案

1. **只手写一份 `.claude-plugin/marketplace.json` 作为唯一事实源。**
   其他平台的清单一律由脚本导出——手改 Cursor 清单的 PR 一律拒绝，
   否则两份清单必然漂移。
2. **导出器读源清单生成 `dist/cursor/`。** 字段一一映射，
   不做任何智能转换——转换逻辑越聪明，排查越痛苦。

## 不做什么

- 不做自建 registry API——当前 4 个插件撑不起一个服务；
- 不适配 Gemini CLI——其生态正在换代，等稳定再接。

## 备选

| 方案                              | 否决原因                                 |
| --------------------------------- | ---------------------------------------- |
| 每平台手写一份清单                | 违反方案第 1 条，漂移只是时间问题        |
| 用 JSON Schema 工具链自动双向同步 | 双向同步需要解决冲突合并，复杂度远超收益 |

## 待定

Cursor 官方市场提交流程是否接受 dist 导出物——不阻塞 draft 评审。
```

**好在哪**：

1. 问题两句讲完，没有发展史；
2. 方案两条都有具体动作和拒绝条件，评审人能直接说同意或反对；
3. 「不做什么」堵住了两个必然被问到的方向；
4. 备选表每条否决原因都对得上方案条款；
5. 全文不到一屏，但决策所需的全部信息都在。

## 架构选型与自建论证型好坏对照（反华而不实）

涉及「自研微服务框架/底座 vs 开源方案选型」等重头架构论证时，最常见的失败方式是**看似技术硬核，实则充满营销嘴炮、虚构假想敌与虚假安全感**。

### 华而不实的典型坏例表现

1. **充斥营销大词与神话**：「独创四类契约」「一锤定音」「彻底解决」「绝对安全」「AI绝无幻觉」——评审专家看到只会认为作者缺乏敬畏与工程常识；
2. **立弱鸡稻草人恶意拉踩**：把 Uber Fx 贬为「只会反射 panic 的大敌」，把 Gin 贬为「停机残缺」，拿专做跨进程隔离的 HashiCorp go-plugin 当假想敌，却漏掉真正同生态机制最接近的 `oklog/run`；
3. **混淆蓝图与现状**：把规划中尚未落地的组件（如异步任务池、Cron 调度、未来 RPC Server）当成已实现的既有优势大肆宣扬；
4. **虚假安全感与违反物理规律**：宣称「通过 context.WithoutCancel 实现请求先排空绝对安全」，无视 Go 协程无法抢占杀死、父取消剥离后无超时导致的泄漏风险、以及下游依赖先响应 cancel 导致的在途级联故障；
5. **不敢写退出条件**：只吹自建收益，不敢给出「出现什么情况表明自建失败、应推翻重回开源」的反悔机制。

### 工业级可信的好例特征

1. **定位克制，边界极窄**：「选择自建不是因为开源无法实现，而是因为需要集中维护的契约足够薄；定位于轻薄装配层，不承诺全能框架」；
2. **最强反驳原则（Steelman）**：公允分析 Fx（承认其有 ValidateApp 校验能力，仅因本项目无通用运行时 DI 需求而放弃）、公允分析 GoFrame（相似能力组织，作为分工参考非敌人）、引入真正对手 `oklog/run`；澄清 go-plugin 属不同范畴；
3. **现状与规划严格隔离**：表格化清点工作树实况（已有 Worker 契约 vs 规划中的 Async/Cron 示例），绝不透支未来信用；
4. **物理极限坦诚自白**：明确说明 30s 是协作式预算，无法强制终止协程；明确说明下游先退出可能连带影响在途请求；明确说明 hijacked 连接标准库不负责；
5. **明确设立重新评估与放弃条件**：列出 4 种具体指标（如演化出任务队列/调度平台、需要通用 DI 时），一旦触发立即重评放弃自建切回开源；
6. **核验依据双栏落盘**：文末列出仓库现行实现代码路径与开源官方标准库/仓库一手链接。
