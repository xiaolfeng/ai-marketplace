# spec-er · 规范模式（含 `draft → rfc → adr` 演进）

公共约定：[../_shared/conventions.md](../_shared/conventions.md) ·
Scope 词表：[../_shared/scope-manage.md](../_shared/scope-manage.md) ·
流转与状态：[../_shared/lifecycle.md](../_shared/lifecycle.md) ·
语言纪律：[../_shared/writing-style.md](../_shared/writing-style.md)

## 模式定位：跨模块规则与长期红线

- **与 `design-er` 的边界**：`design` 针对具体某个功能或系统模块回答「怎样实现与工作」；`spec` 针对**跨模块的通用标准、契约格式、工程约定或架构禁令**回答「必须遵守什么规则、禁止什么写法、如何判定合规」。
- **单文件三阶段原位演进**：
  - **`draft`**（起草）：新建默认态，梳理痛点与初步规则条款；
  - **`rfc`**（提案描述）：规则条款、例外边界、正反例与否决项已完备，供评审讨论；
  - **`adr`**（定稿约束）：经人工确认拍板后升级，清零「待确认」并冻结为长期硬约束（此后不可直接改写核心条款，推翻须新建规范并互标 `superseded`）。

## 操作流程

复制此清单并随做随勾：

```
规范进度：
- [ ] 1. 确认约束的是跨模块/长期规则（单一模块的具体实现 → 转 design-er）
- [ ] 2. 判定动作：新建规范（默认状态 draft） vs 演进既有规范（draft → rfc → adr）
- [ ] 3. 按统一主骨架编写条款：每条规则必须写明「必须/允许什么 + 禁止什么 + 为什么」，并做「单独引用测试」
- [ ] 4. 补齐正反例、豁免边界、违反时的暴露/拦截方式与否决项，消灭「原则上」「尽量」等含糊词
- [ ] 5. 新建时只扫 docs/engineering/spec/ 取最大编号 +1，命名 NNNN-<scope>-<title>.md 落盘；演进时原文件原位更新
- [ ] 6. 同步登记或更新 docs/README.md 的「规范模式（spec）」分表，回报路径与阶段状态
```

## 文档骨架（统一主骨架，按阶段收敛）

```markdown
# 标题

> 状态：draft | rfc | adr · 日期：YYYY-MM-DD · Scope：<scope>
> 承接：[调研/前序文档标题](../research/NNNN-scope-title.md)（如有）

## 适用范围与背景

哪段工程约定容易漂移、为什么必须立规矩，以及本规范管辖哪些目录/模块、明确不管辖什么。一两段话直奔主题。

## 规范条款

编号条款。每条 = **必须/允许什么 + 禁止什么 + 为什么**。
严禁出现「原则上」「尽量」「视情况而定」——要么要求，要么禁止；确有例外必须在条款内写明精确豁免条件。

## 正反例与边界

给出具体可对照的合规写法（✅）与违规写法（❌），并标明容易被误伤的合法边界场景。

## 合规与后果

- **收益与代价**：遵守本规范得到什么、放弃了什么便利；
- **校验与暴露方式**：通过哪条命令/CI 门禁自动拦截，或违反时会在哪里暴露；
- **重评条件**：当项目规模或外部环境发生什么具体变化时，重新评估或废止本规范。

## 否决项

一行一条：被否决的替代规则 | 为什么不行（防止三个月后有人重走老路）。

## 待确认

- `draft` / `rfc` 阶段：列出尚在讨论的争议条款及是否阻塞定稿；
- `adr` 阶段：必须全部清零（写「无（已于 YYYY-MM-DD 定稿冻结）」）。
```

## 定稿纪律

1. **单独引用测试**：把「规范条款」中的任意一条单独复制贴进 Code Review 评论，读者不看上下文也能明确知道该怎么改；做不到就补齐主语和条件；
2. **`adr` 锁定不可直接改**：规范升为 `adr` 后若需调整规则，新增一篇 `spec`，新旧文首互链并将旧文标为 `superseded`；
3. **`adr` 由人拍板**：技能不得未经用户确认直接把新建文档标为 `adr`。
