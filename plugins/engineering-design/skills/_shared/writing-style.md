# 输出语言纪律

五个写作技能（`research-er` / `design-er` / `spec-er` / `runbook-er` / `plan-er`）共用。
目标：写给人看的中文技术文档，不是汇报腔的 AI 生成物。本文件是硬约束，写作时逐条对照。

## 要什么

1. **直接**。第一句就进主题。背景最多两句；
2. **具体**。用具体动词和名词：「删除了 X 函数」而不是「对相关代码进行了优化调整」；
3. **短句优先**。一句话只装一个判断。长句只用于真正的因果展开；
4. **段落各管一件事**，且必须推进论证或提供信息；
5. 列表只用于真正并列的条目（步骤、对比项、规则条款），叙事内容用段落。

## 不要什么

| 类型         | 禁止项                                                                               |
| ------------ | ------------------------------------------------------------------------------------ |
| 空话词       | 赋能、抓手、闭环、沉淀、全方位、深度、极致、完美、强大的                             |
| 技术吹嘘大词 | 一锤定音、独创、绝对安全、彻底管死、零反射/零成本（未实测）、AI 绝不幻觉、工业级屏障 |
| 万能句式     | 「不仅仅是 X，更是 Y」「综上所述」「总而言之」「这不禁让人思考」                     |
| 自问自答     | 「那么该如何做呢？答案是……」——直接说答案                                             |
| 元话语       | 「看完上文我们再来看」「下面将介绍」——删掉后文章照样通顺                             |
| 复读         | 结尾把前文复述一遍；结尾只放前文没说过的收束或下一步                                 |
| 形容词堆砌   | 「优雅的、高效的、可扩展的架构」——改成它到底怎么可扩展                               |

## 技术真实性纪律（反华而不实）

架构设计（`design`）、技术规范（`spec`）、选型调研（`research`）以及处于 `rfc` / `adr` 阶段的文档必须严格遵循以下六条硬门禁，违背任何一条即判定为华而不实：

1. **最强反驳原则（Steelman Principle，反稻草人拉踩）**：
   - 严禁为了论证自研合理性而刻意贬低成熟开源方案（例如：把 Uber Fx 贬为「只会反射 panic」、把 Wire 贬为「毫无用处」、把 Gin 贬为「停机残缺」、把跨进程 go-plugin 拉来与进程内接口对比）；
   - 对比开源竞品或备选规则时，必须以其**官方推荐的最佳姿态与合规用法**作为基准，承认其成熟度与适用场景，仅从「契约规模是否足够薄」与「团队适配成本」切入。
2. **现状与规划严格隔离（Reality vs. Roadmap）**：
   - 严禁把未来规划、尚未合并的原型或概念设想（如「未来 gRPC Server / 异步任务池」）写成当前架构的既有能力；
   - 必须显式设立工作树现状声明：哪些是当前工作树已有且已验证的代码，哪些是后续规划（或交由 `docs/plan/` 分期推进），两者必须表格化分流，严禁透支未来信用。
3. **物理常识与失效自白（Physics Realism & Failure Modes）**：
   - 严禁向读者提供虚假的安全感（例如：宣称「在途请求先排空，开箱即用绝对安全」而无视下游已被 cancel 级联失败、协程不可强制抢占等运行时物理规律）；
   - 必须坦诚说明极限条件下的表现与失效行为（如超时强制退出、不响应取消的泄漏风险、长连接/hijacked 连接的逃逸）。
4. **自研与硬约束必须带重新评估与退出条件（Re-evaluation & Exit Criteria）**：
   - 任何自建底座或严苛规范的决定（尤其进入 `rfc` / `adr` 阶段时），都必须给出反悔机制：明确列出「当出现哪几种具体条件时，表明当前方案或规范维护成本已失控，团队应推翻重评」。
5. **管理边界清晰化（不搞大包大揽）**：
   - 明确指出自身管理的是什么、坚决不管理的是什么（即「不做什么」）。禁止在设计或规范中把薄层包装吹成全能平台。
6. **核验依据双栏落盘（Evidence Grounding）**：
   - 关键主张必须挂钩具体源码路径，对比项必须链接官方文档、标准库包源码或真实 issue；严禁只有断言、没有出处。

## 删减测试

改完每段做一遍：删掉这个词/这句，重读。

- 句子只是变短了 → 保持删除；
- 失去了精确含义 → 恢复。

## 自由度对照

| 内容                         | 约束强度                   |
| ---------------------------- | -------------------------- |
| 编号、命名、目录落点、状态值 | 死命令，照抄规范           |
| 文档骨架                     | 按各模式模板，核心块不可缺 |
| 行文语气                     | 按本文件的原则，措辞自由   |
