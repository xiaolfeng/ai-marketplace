# Scope 管理：业务域词表（工程文档侧）

写作技能与 doc-clean 共用。
本文与 git-manage 的同名文件共用同一套定义：**Scope 就是业务域**——
从项目业务里分析出的一类业务环境，如养成系软件的 用户(user)、树洞(treehole)。
目录落点见 [conventions.md](./conventions.md)，流转与状态见 [lifecycle.md](./lifecycle.md)。

## Scope 在文档命名里的位置

文件名 `NNNN-<scope>-<title>.md` 的 `<scope>` 段回答
「这份文档讨论的是哪个业务域」。它与目录正交：

- 目录名（draft / research / rfc / design / adr）表达**生命周期阶段**，不是 Scope；
- `<scope>` 表达**业务域**，一律取词表的英文单词列（小写、单个词）。

示例：养成系软件的树洞匿名提案 → `docs/engineering/rfc/0003-treehole-anonymous.md`

## 权威词表

唯一登记处是项目根的 `docs/scope-manage.md`（下称「台账」），本文不留副本。
每个 Scope 同时登记三个名字（2 字中文 / 4 字中文 / 英文单词），
工程文档只消费其中英文单词列。

## 使用流程

1. 动笔前先查台账：要写的主题属于哪个既有业务域？取其英文单词列；
2. 找不到贴切业务域时不要硬套：为新域同时起三个名字
  （2 字中文 / 4 字中文 / 英文单词），请用户确认后登记进台账，再回来取英文列；
3. 编号按 conventions：只在目标阶段目录内取最大值 +1。

## 防同义词纪律

1. 中英任一名字列语义命中即视为同一 Scope——禁止为同一业务域另造英文别名
  （如已有 `treehole` 就不得再用 `secret`、`confession`）；
2. 废弃的业务域在台账标注去向，历史文档不改名；
3. 台账不存在时先用 docs-init 补骨架，再走登记流程，不得绕开台账自造词。

## 边界判例

| 情形 | 正确动作 |
| --- | --- |
| 主题横跨两个业务域 | 取主要归属域；确需拆分则拆成两篇各带自己的 scope |
| 讨论对象是仓库自身而非外部业务 | 视仓库性质登记一个基础设施域（如本仓的 `marketplace`）|
| 只是想给某篇旧文补个疑问 | 评论留在原文，不新建档 |
