# 特殊情况处理手册

SKILL.md「特殊情况速查」的完整处置步骤。每条给出判定信号与处置动作，
问询编号（Q1~Q5）对应 SKILL.md「问询协议」。
所有条目的共同前提：铁律仍然生效——绝不 push、不加 `Co-Authored-By`、提交信息用中文。

## E1 空仓库 / 无提交历史

**信号**：`git log` 报错
`fatal: your current branch 'main' does not have any commits yet`（分支名可能不同）。

**处置**：

1. 跳过 `git log`，其余分析照常进行；
2. 无命名先例可循时，首次提交推荐：
   - 初始内容为脚手架/配置 → `chore: 初始化项目`
   - 初始内容即为可运行的功能实现 → `feat: 初始化项目`
3. Scope 省略（业务域词表尚未建立）；
4. 台账 `docs/scope-manage.md` 不存在属正常现象，此时不触发 Q4，
   留到之后首次需要写 scope 的提交再决议。

## E2 敏感文件 / 凭证混入

**信号**：待提交列表出现 `.env`、`*.pem`、`*.key`、`id_rsa*`、`credentials*`、
`*.keystore` 等文件，或内容疑似 token / 密码；
也包括未被 ignore 的体积异常产物（`node_modules/`、`dist/`、`.DS_Store`）。

**处置**：

1. 先查 `.gitignore` 是否遗漏——遗漏时补一行并纳入本次提交；
2. 按问询协议 Q2 询问：「检测到疑似敏感文件 X，建议将其移出本次提交
   并补充 `.gitignore`，是否同意？」（默认推荐移出）;
3. 用户同意排除 → 未暂存则不动它，已暂存则 `git restore --staged <file>`，
   补 `.gitignore` 后提交其余文件；
4. 无论用户作何选择，都在最终返回结果里点名该文件的处置方式。

禁止自作主张把敏感文件留在提交里；也禁止未经确认擅自删除用户文件。

## E3 合并进行中 / 存在未解决冲突

**信号**：`.git/MERGE_HEAD` 存在；或 `git status` 显示 `Unmerged paths`；
或 `git diff` 内容中出现 `<<<<<<<` 冲突标记。

**处置**：

1. **仍有未解决冲突** → 不做任何提交。输出冲突文件清单后停止，
   提示用户解决冲突后重新发起提交（对应铁律 5 的"不可自动解决的冲突"）；
2. **冲突已全部解决**（status 中只剩 staged 变更）→ 正常走本技能流程。
   合并提交同样遵守格式规范，scope 取本次合并引入的主要业务域；
3. 不要主动执行 `git merge --abort` 或 `git rebase --abort`。

## E4 pre-commit / commit-msg hook 失败

**信号**：`git commit` 非零退出，输出中含 hook 名称与失败原因
（如 lint-staged、husky、pre-commit framework、commitlint）。

**处置**：

1. 把失败 hook 名称与报错原样汇报给用户；
2. 失败点可机械修复（格式化、import 排序等 lint 自动项）→ 修复后重试提交；
3. 需要跳过 hook 时（`--no-verify`）必须经用户明确同意——属问询协议 Q3 范畴；
4. 连续两次修复仍失败 → 停止重试，报告现场等待用户指示。

## E5 detached HEAD

**信号**：`git status` 显示 `HEAD detached at <hash>`。

**风险**：此时的提交不挂在任何分支上，切走后即成为孤儿提交。

**处置**（属问询协议 Q3）：

1. 向用户说明现状与风险；
2. 给出选项：
   - 先建分支再提交：`git switch -c <branch-name>`（推荐）
   - 确认就在 detached HEAD 上直接提交；
3. 用户选定后再继续正常提交流程。

## E6 用户要求 push

**信号**：用户说"帮我推上去"、"push"、"提交并推送"等。

**处置**：

1. 先正常完成 `git add` + `git commit`；
2. 明确告知 push 不在本技能职责内，话术：
   「已完成提交 `<hash>`；按约定我不执行 push，请自行推送。」
3. 即使用户坚持要求，也不执行任何 `git push` 变体（含 `--force`），
   请用户手动操作。

## E7 海量删除 / 全库换行符批量变更

**信号**：diff 中删除文件数异常多（如 ≥10 个或占比过半）；
或几乎所有文件仅行尾符/空白差异（CRLF/LF 转换、编辑器批量格式化）。

**处置**（属问询协议 Q3），先区分两种情况：

1. **真实批量删除**（重构、废弃模块）→ 向用户列出删除清单概要，
   确认后按普通流程提交，正文建议说明删除原因；
2. **行尾符/空白噪音** → 建议配置 `.gitattributes` 或修正本地设置，
   避免一次性污染全仓 blame 历史；经用户确认后选择照常提交或回退这批变更。

## E8 子模块指针变化

**信号**：`git status` 中子模块显示 `modified: <submodule> (new commits)`。

**处置**：

1. 作为主仓的普通变更提交（暂存的是子模块指针哈希）；
2. scope 归主仓业务域，不进入子目录替子仓提交；
3. 正文可注明子模块更新的目的版本或原因，便于回溯。
