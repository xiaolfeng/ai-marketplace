# 端到端场景演练

从「用户说提交」到「返回哈希」的完整动作序列。
Q1~Q5 对应 SKILL.md「问询协议」，E1~E8 对应 [../references/edge-cases.md](../references/edge-cases.md)。

## 场景 A · 单模块常规提交（最常见路径）

**状态**：改了 `user` 模块的三个文件，台账已决议采用 2 字中文。

```
git status    → 3 个 modified
git diff      → 新增预设增删改接口与参数校验
git log       → feat(用户): ... / fix(树洞): ...
```

**动作**：类型 `feat`，scope 查台账得「用户」，标题行通过自检，
直接 `git add -A && git commit`。

**返回**：

```
✅ 已提交 abc1234
feat(用户): 添加 AI 语气预设管理接口
```

## 场景 B · 多模块默认单次提交

**状态**：同时改了 `user` 与 `treehole` 两个模块（升级公共依赖引发的连带修改），
用户只说了"提交"。

**动作**：默认不拆分（铁律 4）。横跨多个功能模块 → scope 省略：

```
✅ chore: 升级框架至 5.2 并适配两处废弃 API 调用
```

禁止主动询问"要不要拆成两次"；只有用户明确要求时才转入场景 E。

## 场景 C · Q4 —— 首次写 Scope 且采用模式未决议

**状态**：新项目首次需要写 scope，根目录无 `docs/scope-manage.md` 台账。

**动作**：停下，用多选题提问（一次一个问题）：

> 本项目首次使用提交作用域（scope），请选择书写模式，决议后永久沿用：
>
> ① **2 字中文**（推荐）—— 示例 `feat(用户): 新增签到接口`
> ② **4 字中文** —— 示例 `feat(用户模块): 新增签到接口`
> ③ **英文单词** —— 示例 `feat(user): 新增签到接口`

**答复后**：创建台账并回填「采用模式」与新 Scope 三名列，然后立即继续提交，
不再二次确认。

## 场景 D · Q2 —— 检出敏感文件

**状态**：diff 中除业务代码外，还出现了 `.env.local`（含数据库密码），
且 `.gitignore` 未覆盖它。

**动作**：

1. 先补一行 `.env.local` 进 `.gitignore`；
2. 提问：「检测到疑似敏感文件 `.env.local`，建议移出本次提交并已补充
   `.gitignore`。是否按此处理？（推荐）／ 或仍将其一并提交？」
3. 用户同意 → `git restore --staged .env.local` 后提交其余文件；
4. 返回结果中点名处置方式：
   「✅ 已提交 `<hash>`；⚠️ `.env.local` 已排除并加入 `.gitignore`。」

## 场景 E · 用户明确要求拆分

**状态**：改动含「新功能 + 缺陷修复」，用户说"分两次提交，功能和修复分开"。

**动作**：按主题分组，分别暂存、分别提交：

```bash
git add src/modules/treehole/          # 功能相关文件
git commit -m "feat(树洞): 实现匿名发帖冷却限制"
git add src/modules/user/              # 修复相关文件
git commit -m "fix(用户): 处理头像上传超大文件报错"
```

**返回**：逐条列出每个哈希 + 对应信息。拆分粒度以用户的说法为准，
不再追问"这样拆可以吗"。

## 场景 F · 用户要求 push

**状态**：用户说"提交完顺便推上去"。

**动作**：正常完成 commit 后回复：

> ✅ 已提交 `abc1234` — `fix(树洞): 解决会话创建时空指针异常`
> 按约定我不执行 push，请自行推送。

即使用户再次坚持，也不执行任何形式的 `git push`（铁律 1，见 edge-cases E6）。
