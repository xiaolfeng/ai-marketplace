# Git Commit —— 提交信息生成与执行

分析当前仓库的代码变更，生成规范的中文提交信息，并直接执行 `git commit`。
本技能是提交**执行器**而非提交建议器：完成 diff 分析后立即提交，
最终交付物只有一项——提交哈希 + 最终提交信息。

## 变更分析

按顺序采集仓库实时变更数据：

- `git status`
- `git diff`
- `git diff --staged`
- `git log --oneline -10`

命令报错时不中断流程，按 [references/edge-cases.md](references/edge-cases.md) 对应条目处置：
无历史提交的仓库跳过 `git log`；合并进行中、detached HEAD 等状态先走特殊流程再回来提交。

根据以上 diff 判断：改了哪些模块？变更本质是什么？
（是否拆分提交由铁律 4 决定——默认不拆。）

## 铁律

1. **只 commit，绝不 push。** 禁止执行 `git push` 或任何远程推送操作。
2. **禁止在提交信息中添加 `Co-Authored-By` 或任何共同作者字段。** 提交作者就是用户本人。
3. 提交信息必须用中文编写（除非项目历史明确使用英文）。
4. **默认一次提交。** 无论改动跨多少模块/文件，默认合并为单次 commit。只有当用户明确要求"按功能/分类/模块拆分"、"分几次提交"时，才拆分为多次 commit。不要主动建议或询问是否拆分。
5. **直接执行，不要把决策推回给用户。** 这是提交**执行器**，不是提交建议器。完成 diff 分析后立即 `git add` + `git commit`，禁止问"是否需要提交"、"提交信息这样可以吗"、"要不要拆分"。分析 diff 的唯一目的是写出准确的提交信息，不是为了征求确认。允许停下来询问的情形只有下方「问询协议」列出的封闭清单，清单之外一律不许问。

## 问询协议

下表是**唯一的**允许提问清单，表外情形一律直接执行：

| 编号 | 触发情形 | 动作 |
| --- | --- | --- |
| Q1 | diff 为空或全部变更均已提交 | 不提问，报告现状后结束 |
| Q2 | 待提交内容中检出敏感文件或疑似密钥（`.env`、`*.pem`、凭证等） | 二选一：移出后提交其余（推荐）/ 照常全量提交 |
| Q3 | 危险操作：大量删除、重写历史、强制覆盖、detached HEAD、跳过 hook | 说明风险与后果，等待用户明确指令 |
| Q4 | 需要写 Scope 但台账未决议「采用模式」 | 三选一：2 字中文（推荐）/ 4 字中文 / 英文单词 |
| Q5 | 变更意图无法从 diff 与 `git log` 推断，类型或描述拿不准 | 给出 2~3 个候选理解（各附提交信息草案）供用户挑选 |

提问方式：

1. 用带选项的多选题形式提问（如 `AskUserQuestion` 工具），一次只问一个问题；
2. 每个选项附一句影响说明，并标注推荐项；
3. 得到答复后立即继续提交流程，不复述、不再二次确认。

话术示范见 [examples/scenarios.md](examples/scenarios.md) 场景 C / D / F。

## 执行步骤

### 1. 选类型

根据**变更本质**选择。速查：
`feat` 新功能 · `fix` 缺陷 · `perf` 性能 · `refactor` 重构 · `docs` 文档 ·
`style` 格式化 · `test` 测试 · `build` 构建/依赖 · `ci` 流水线 · `chore` 杂项 · `revert` 回滚。
拿不准时以「变更本质」复核：修了错误行为是 fix，行为不变动结构是 refactor；
仍拿不准且影响交付时按问询协议 Q5 处理。

### 2. 选作用域 (scope)

完整定义、采用模式与新建流程见
[../_shared/scope-manage.md](../_shared/scope-manage.md)。速查：

Scope 即业务域，全项目一套词表，登记在根目录 `docs/scope-manage.md`。
首次需要写 scope 而台账未记「采用模式」时，按问询协议 Q4 让用户三选一并回填台账：

```
feat(用户): …    ← 采用模式 = 2 字中文
feat(user): …    ← 采用模式 = 英文单词
```

粒度优先级：**功能模块 > 技术层级 > 子系统 > 省略**
（功能模块 `用户`·`树洞` · 技术层级 `接口`·`配置` · 子系统 `mcp` · 多模块/全局省略）

新建 scope：先查台账词表 + `git log` 复用；确属新域则把三名列
（2 字中文 / 4 字中文 / 英文单词）一次起齐，请用户确认后登记进台账。

### 3. 写标题行

格式：`<类型>(<作用域>): <描述>`

规则：
- 首字母小写，无句号，现在时态
- 动词开头 + 具体对象（禁止空泛词汇）
- <= 50 字符

**动词速查：** 新增->添加/实现/创建 | 修复->修复/解决/处理 | 改进->优化/改进/增强 | 移除->移除/删除/废弃 | 调整->调整/修改/更改

```
❌ fix: 修复缺陷              ❌ feat: 更新代码
✅ fix(树洞): 解决会话创建时空指针异常
✅ feat(用户): 添加 AI 语气预设管理接口
```

更多好坏对照见 [examples/messages.md](examples/messages.md)。

### 4. 决定正文

日常提交通常不需要。以下情况考虑加：
- 需要解释**为什么**这么做
- 涉及架构决策或取舍
- 修复难以复现的问题

模板（每行 <= 72 字符）：

```
<类型>(<作用域>): <标题>

原因: 为什么需要这个变更
内容: 具体做了什么
影响: 对其他模块的影响

关闭 #123
```

成品示例见 [examples/messages.md](examples/messages.md) 正文一节。

### 5. 执行提交

1. `git status` 确认文件范围；发现敏感文件按问询协议 Q2 处理
2. `git add` —— 默认把全部相关变更加入暂存（`git add -A` 或逐个 add），**一次提交搞定**
3. `git commit -m "<提交信息>"`；hook 失败按 [references/edge-cases.md](references/edge-cases.md) E4 处置
4. 返回结果：提交哈希 + 最终提交信息

**默认单次提交**：把所有变更打包成一次 commit。仅当用户明确要求"按功能/分类/模块拆分提交"时，才按主题分组，分别 `git add` + `git commit`（演练见 [examples/scenarios.md](examples/scenarios.md) 场景 E）。

## 特殊情况速查

遇到下列信号时，先读 [references/edge-cases.md](references/edge-cases.md) 对应条目再行动：

| 信号 | 处置要点 | 条目 |
| --- | --- | --- |
| `git log` 报错（仓库无提交历史） | 跳过 log，按 E1 定首次提交命名 | E1 |
| `.env`、密钥、凭证出现在待提交列表 | 问询协议 Q2，默认移出并补 `.gitignore` | E2 |
| 合并进行中 / 存在未解决冲突 | 冲突清完才允许提交，否则报告后停止 | E3 |
| pre-commit / commit-msg hook 失败 | 汇报原因；`--no-verify` 须用户同意 | E4 |
| detached HEAD | 先确认分支归属再提交（Q3） | E5 |
| 用户要求 push | 拒绝 push，仅完成 commit 并告知 | E6 |
| 海量文件删除 / 全库换行符批量变更 | 问询协议 Q3，区分真实删除与噪音 | E7 |
| 子模块指针变化 | 作为普通变更提交，scope 归主仓业务域 | E8 |

## 特殊格式

**Breaking Change：**
```
feat!: 移除对旧版 API 的支持
BREAKING CHANGE: 认证方式从 Session 切换为 JWT
```

**关联议题：** `关闭 #123` / `相关 #456`

**回滚：**
```
revert: 回滚 "feat(认证): 添加 OAuth2 集成"
此操作回滚提交 abc1234，原因: 生产环境兼容性问题
```

## 自检

- [ ] 类型准确（fix != refactor）
- [ ] 作用域与台账及项目历史一致
- [ ] 描述：动词开头、小写、无句号、<=50 字符
- [ ] 无空泛词汇
- [ ] 无 `Co-Authored-By`
- [ ] 不包含 `git push`
- [ ] 默认单次提交（除非用户明确要求拆分）
- [ ] 分析完直接 add + commit，没有反问用户确认
- [ ] 敏感文件、危险操作、hook 失败均按问询协议与 edge-cases 手册处置
