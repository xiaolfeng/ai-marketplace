# 分支操作安全手册

need-merge 与 need-rebase 两个技能共用的前置检查与异常处置手册。
共同前提：只操作本地分支，绝不执行任何形式的 `git push`（含 `--force-with-lease`），
推送永远由用户自行完成。发现异常时用多选题形式提问（一次一个、附推荐项），
得到答复后立即继续，不再二次确认。

## 参数语义

两个技能共用一套心智模型：**源分支是被搬运的分支，目标分支是基准分支**。

| 用户说 | 源 | 目标 |
| --- | --- | --- |
| 「把 A 合并到 B」/「把 A 变基到 B」 | `A` | `B` |
| 只提一个分支名 | 该分支 | 当前分支 |

一个分支名都没提时不要猜：列出本地分支让用户指定源与目标，再按下式取动作。

解析出源与目标后，按技能套用底层动作：

- **need-merge** → `git switch <目标> && git merge <源>`
- **need-rebase** → `git switch <源> && git rebase <目标>` |

方向差异务必分清：

- **merge**：把源的提交搬进目标，停在目标分支上；
- **rebase**：把源的提交重放到目标之上，改写的是**源分支**的历史，最后停在源分支上。

## 前置检查

C1~C4 全部通过才允许动手；任何一条不过就停下来走对应处置：

| 编号 | 检查 | 命令 | 不过时的处置 |
| --- | --- | --- | --- |
| C1 | 分支存在 | `git rev-parse --verify --quiet refs/heads/<branch>` | 本地不存在时查 `refs/remotes/origin/<branch>`：仅有远程分支 → 二选一（建跟踪分支继续 / 中止）；两者都无 → 报告后结束 |
| C2 | 源 ≠ 目标 | 比较两个参数 | 同名直接拒绝并提示正确用法 |
| C3 | 工作区干净 | `git status --porcelain` 非空即脏 | 三选一：stash 后继续（推荐）/ 先提交（转 git-commit 技能）/ 中止 |
| C4 | 无进行中操作 | `.git/MERGE_HEAD`、`.git/rebase-merge`、`.git/rebase-apply` 任一存在 | 报告进行中的操作名称与残留状态，停止；待用户处理完再来 |

## 方向一致性检测（防误操作核心）

参数解析完成后、动手之前，先采集两个区间：

```bash
A=$(git log --oneline <dst>..<src>)   # 源有而目标没有 → 本次要搬运的内容
B=$(git log --oneline <src>..<dst>)   # 目标有而源没有 → 目标领先的部分
```

按下表判定，命中「必须确认」行就用多选题向用户核实方向，不得自作主张继续：

| 现象 | 解读 | 动作 |
| --- | --- | --- |
| A 为空 | 源没有任何目标缺少的提交——要么两分支已同步无事可做，要么**方向填反了** | 必须确认：回显两个分支名与最近各 3 条提交，二选一（交换方向重来 / 确认无需操作） |
| A 超过 50 条 | 可能拿错分支，或是久未同步的大批量合并 | 必须确认：给出条数与前 10 条标题，二选一（继续 / 中止） |
| B 为空（merge） | fast-forward，正常路径 | 直接继续，回报时注明 ff |
| B 很多（rebase） | 正常——源将被重放到目标最新提交之上 | 回报时注明重放数量即可 |
| 源是主干分支（main / master / develop 等）而目标像特性分支 | 方向合法但少见，大概率参数填反 | 必须确认：二选一（方向无误继续 / 交换方向） |
| 两分支名高度相似（如 `feat/x` 与 `fix/x`） | 手滑高发场景 | 必须确认：回显完整分支名与各自 HEAD 摘要让用户核对 |

## 历史改写警告（仅 need-rebase）

执行前检测源分支是否绑定了上游：

```bash
git rev-parse --verify --quiet refs/heads/<src>@{upstream}
```

上游存在时，rebase 会改写已推送的历史，之后推送必须 force-with-lease 且可能影响其他协作者。
此时必须先向用户确认：「源分支 `<src>` 已推送到远端，变基后需要强制推送覆盖远程历史，
确定继续吗？」——得到明确同意后才执行；不同意则中止。
无论结果如何，本插件都不代为推送，完成后提醒用户自行决定推送方式。

## 冲突处置

merge 或 rebase 出现冲突时：

1. 列出冲突文件清单与每个文件的冲突块数量，然后停止；
2. 默认不自动解决——冲突取舍属于业务判断；
3. 用户明确要求代为解决时，逐文件展示解决方案再落盘，一次一个文件；
4. 逃生口只有一条路：用户同意后执行 `git merge --abort` / `git rebase --abort` 还原现场；
5. 衔接：冲突解决完毕后的收尾提交遵循 git-commit 技能的提交规范。

## 回报格式

**成功**：

```text
✅ <merge 完成 / rebase 完成>
<源> ➜ <目标> · 搬运 N 个提交 · HEAD <hash>[ · fast-forward]
[rebase 且源已推送时追加] ⚠️ 远程历史已分叉，推送需 force-with-lease，请自行执行
```

**失败或中止**：停在哪一步、触发哪条检查、当前现场状态、恢复方法（如 abort 命令）。
