# 逆向解构与因果复盘方法论（Reverse Deconstruction Methodology）

本文件是 `replay-md`、`replay-html`、`replay-post-md`、`replay-post-html` 四个技能共用的核心分析引擎；拆解阶段不区分读者，口吻与脱敏在落笔阶段按 [audience-voice.md](audience-voice.md) 处理。
当用户面对长篇 AI 会话记录（`.jsonl`、导出文本、终端日志）、多轮代码变更（PR / Commit 序列）或复杂排障演练，感到「AI 猛猛做了一大堆、我一直在点同意、虽然做成了但我已经完全懵了」时，必须严格按本方法论完成**逆向解构**，再输出为目标格式。

---

## 一、 为什么人会在 AI 猛猛干活时彻底懵掉？

人类在阅读或经历 AI 长对话时陷入混淆，根源不是「智商不够」，而是**工作记忆被四类信息结构击穿**：

1. **顺向流水账噪声（Chronological Noise）**：AI 为了查清一件事，会连续试探 15 个文件、失败 4 次命令、修 2 次脚本语法。按时间顺序看，主线被淹没在试错细节里。
2. **隐式跳转（Implicit Jumps）**：AI 读完 A 文档的第 20 节，脑子里已经算出了「所以不能改 B 配置，必须去建 C Issue」，但回复里只冷冰冰地甩出一句「接下来我去建三个 Issue」，人类根本不知道**为什么突然从代码审查跳到了建 Issue**。
3. **跨层并发（Interleaved Threads）**：AI 在等 CI 或后台压测的 10 分钟里，顺手去修了另一篇文档的 Snowflake ID 脚本报错，又回来处理团队通知草稿。多线程穿插让因果链断裂。
4. **同名异义 / 概念纠缠（Concept Entanglement）**：比如「代码已合入 main」但「环境里秒杀功能还是关着的」，或者「canary」与「qa-bench」轮番出现，人类如果不清楚底层的开关机制与环境定位，就会在来回切换中迷失。

## 二、 核心心法：终局倒推，正向走读

> **分析时从终局往回扒（Backward Tracing），讲述时从起点往前走（Forward Walkthrough）。**

### 第 1 步：锚定终局账单（End-State Inventory）

先不要扎进第 1 行对话！直接跳到最后，盘点这场会话/变更到底留下了哪些**真实世界的状态改变**：

- 代码与分支：合入了哪个 PR？新开了哪个 PR？留下了哪些 Commit（还是做了 Revert）？
- 外部协作件：新建或重开了哪些 Issue？发出了哪几条团队通知/评论同步？
- 环境与运行态：哪个集群/环境被改了？最终停在什么镜像版本？
- 悬置未决项：最后还有什么事没做完、卡在谁手上？

### 第 2 步：逆向追问「为什么会有它？」（Backward Causal Tracing）

拿着终局账单里的每一项产物，逆向往回找它的**直接触发点（Trigger）**：

```text
终局产物 X（如：新建手册 PR #149 并在 canary 环境排期）
  ↑ 为什么不直接改 k8s-gitops，而要写手册去 canary 演练？
中间发现 Y（查平台发布规范发现：改 RollingUpdate 前必须先过 1→2→1 多实例演练，且挂在总控单 #105 下）
  ↑ 为什么突然去查平台发布规范？
前序阻塞 Z（架构评审人在 PR #146 提出：负载均衡器在单实例替换期间有 15s+ 的 502 空窗，验收标准不降）
  ↑ 为什么评审人会来补审 PR #146？
初始起因 W（前序脚本未等人工评审直接把 #145 合进了 main 并关了 #140，用户要求重开 Issue 并建 #146 作为合并后补审锚点）
```

一旦逆向追通这条链，原本散乱的数千行记录就会自动挂接成一棵主干清晰的因果树！

### 第 3 步：四类噪音折叠（Noise Folding Rules）

在把因果树转成步进关卡（Steps）时，必须把以下四类过程折叠进对应 Step 的「小插曲 / 排障折叠区」，**严禁将它们单独列为主线 Step**：

| 噪音类型            | 典型表现                                                                               | 折叠处置规则                                                                             |
| ------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| **N1 工具试错**     | 命令粘贴截断、`<你的配置>` 占位符原样执行报错、`$ns：` 中文冒号导致 bash 变量未定义    | 合并为当前 Step 下的一句「排障插曲：修复脚本语法与 kubeconfig 权限」，只留最终跑通的命令 |
| **N2 后台等待穿插** | 等压测 B 跑 10 分钟期间顺手修了手册里的 Snowflake ID 写法                              | 按逻辑归属拆分：Snowflake ID 归入「代码与文档小修」步，压测结果留在「环境演练」步        |
| **N3 方向折返**     | 先提议改用 qa-bench 并提交了 `1a2b3c4`，后因团队敲定 canary 又用 `5d6e7f8` Revert 撤回 | 聚合成一个「认知辨析节点」：直接讲清「为什么曾想切 qa-bench、为什么最终锁死 canary」     |
| **N4 话术打磨**     | 通知草稿改了 3 版（删多余段落、改频道广播为话题内回复、修正演练定性措辞）              | 只保留最终定稿的核心口径与「为什么要这样改措辞」的业务原因                               |

### 第 4 步：切分 5–9 个「认知关卡（Step）」

人类一次复盘最舒适的步进粒度是 **5 到 9 步**（超大型会话最多不超过 12 步）：

- 如果少于 4 步：说明过度概括，沦为了笼统的总结报告，失去了「一步一步带我走出来」的颗粒度；
- 如果多于 12 步：说明把工具调用当成了步骤，读者点「下一步」会点到麻木。

每个 Step 必须代表一次**认知位移（Cognitive Shift）**：读完这一步，读者对系统状态或问题边界的理解往前推了一格。

## 三、 首尾咬合铁律（The Handoff Chain Invariant）

为了让读者产生「顺着一条绳子往下爬」的丝滑感，相邻两步之间必须满足严格的**首尾咬合约束**：

$$\text{Step } k \text{ 的「引申到哪里（Next Hook）」} \equiv \text{Step } (k+1) \text{ 的「第一步看什么（Entry Anchor）」}$$

- **错误示范（断链）**：
  - Step 2 结尾：修完了两处代码日志问题并推送到 PR #146。
  - Step 3 开头：去检查 `~/.kube/nova-qa-token` 配置文件。
  - _读者反应_：？？？怎么突然看起 kubeconfig 了？中间发生了什么？
- **正确示范（咬合）**：
  - Step 2 结尾（引申到哪里）：代码小毛病修完了，但 #140 要求「必须有 qa-bench 环境下的真实启停与排空证据」才能算数——所以我们下一步必须立刻进入 **qa-bench 集群的基线与启停压测**。
  - Step 3 开头（第一步看什么）：看 **qa-bench 集群的订单服务 Deployment 基线与压测脚本**（`drill-00-baseline.sh`）。为什么要看这里？因为上一轮只测了健康检查，没测在途长事务在 Pod 停机时会不会断！

## 四、 迷雾雷达：识别并拆解「用户懵逼点」

在读取对话记录或材料时，重点扫描以下**四类人类困惑信号**，一旦命中，必须在对应 Step 中插入专门的「迷雾破除（Confusion Buster）」模块：

1. **连续无脑同意信号**：用户连续回复「可以」「继续」「按推荐来」「好」「发」超过 3 轮，且中间 AI 输出了长篇多表技术分析 → 说明此处信息密度过高，需提炼「AI 替你拍板的真实权衡是什么」。
2. **追问「为什么」信号**：用户主动发问（如「为什么秒杀功能会关闭，不是合并了吗？」「为什么不能一个环境内做？」「所以 canary 的意义是什么？」） → 这是整场会话最宝贵的认知卡点，必须做成高光问答卡。
3. **紧急叫停 / 方向撤回信号**：出现 `[Request interrupted by user]`、「错错错，就是用 canary 不是 qa-bench」 → 必须解释清楚当时为什么产生分叉、撤回是怎么安全落地的。
4. **跨栈/跨仓跳跃信号**：同一个动作横跨应用仓（`order-service`）、配置仓（`k8s-gitops`）、平台规范仓（`platform-rfcs`）和基础库（`idempotency-kit`） → 必须画出「四仓联动职责表」，标清谁管代码、谁管开关、谁管规范。
