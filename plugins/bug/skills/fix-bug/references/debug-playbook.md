# 系统化修复手法

配合 `fix-bug` 使用。阶段名与 Superpowers 的 systematic-debugging 四段对齐
（先因后补丁、单变量实验、失败三次回到调查），并加上本插件的发现 ID 衔接。

来源：obra/superpowers `systematic-debugging` 技能公开流程（调查 → 模式 →
假说 → 修复）。

## 何时强制走完四段

- 有失败测试、线上堆栈、或「怎么改都不对」；
- 用户点名某条 `Q-xx` / `S-xx`；
- 看起来「一眼就能改」但补丁已经失败过一次。

不要因为赶工或「就改一行」而跳过第 1 段——跳过调查的补丁在本技能里算失败。

## 第 1 段 · 调查（还不许改生产逻辑）

1. 把错误信息、堆栈、失败断言**读完**，不要只看第一行；
2. 写成最小复现：一条测试或一组确定步骤。写不出来就还没理解问题；
3. 看最近相关 diff、依赖升级、配置/环境差异；
4. 多层系统在每个边界打一次进出日志或断言，把断裂层隔离出来；
5. 从错误值往回追到它变成错的那一行。

可以加临时日志或测试，但不要在这一段提交「修复」。

## 第 2 段 · 对照

拿一份**正常**的邻近实现或权威参考，列出每一处差异。
差异不是根因，是假说的候选集。共享可变状态、可选空值、错误被吞，
这三类差异优先怀疑。

## 第 3 段 · 假说

一次只保留一个具体假说（「`order.total` 在折扣后用了整数除法截断」）。
设计只翻转这一个变量的实验。假说失败就换新的，不要把两个补丁叠在一起
「也许这样就好了」。

承认不知道是合法输出。连续两个假说被证伪之后，回到第 1 段，不要开始
霰弹式改文件。

## 第 4 段 · 修复

1. 先有失败的复现（红），再改产品代码；
2. 只改根因对应的不变量；顺手重构放到「故意不改」；
3. 原复现必须变绿；再跑最近的相邻测试；
4. 同一根因的补丁失败满 3 次：停止叠加，当作可能的结构问题写进
   「未覆盖风险」，必要时建议回 `engineering-design` 而不是第四块创可贴。

## 安全缺陷的修复附加规则

修 `S-xx` 时：

- 补丁必须关上报告里指出的那条数据流或授权缺口；
- 验证用授权范围内的回归（合法用户仍能访问自己的资源、非法 ID 被拒），
  不要用利用脚本当测试；
- 涉及密钥/口令：轮换步骤写在修复记录里，密钥值本身不进 diff 说明。

## 反模式（出现即重启第 1 段）

| 信号                                   | 为什么算失败                   |
| -------------------------------------- | ------------------------------ |
| 「先改了再说，根因回头再看」           | 症状补丁，回归必炸             |
| 一次改三处互不相关的地方               | 无法知道哪处生效               |
| 加 `try/catch` 把异常吞掉让测试变绿    | 把发现藏起来                   |
| 加宽类型、加 `any`、去掉断言让编译通过 | 删除信号，不是修复             |
| 用户说「别猜了」仍继续试               | 调查已经宣告破产，必须重读证据 |
| 发现清单是「存疑」却直接出补丁         | 把猜测当成根因                 |

## 与发现技能的衔接

- 有 `Q-xx` / `S-xx`：先复现该条，再修；复现失败则回写排除，而不是硬修；
- 没有编号：先写一句话问题陈述（等价于临时发现），再进入四段；
- 修的过程中撞见新的无关缺陷：记一行转交，不顺手改掉。
