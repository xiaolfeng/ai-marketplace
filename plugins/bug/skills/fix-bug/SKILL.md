# Fix Bug —— 按根因修复

把已经暴露的错误修对，而不是修没。
调查没结束之前不改产品逻辑；补丁必须让原复现变绿，并且只动那一条不变量。

与姊妹技能的分工：

- 还不知道错在哪、要先出清单 →
  [find-bug](../find-bug/SKILL.md) /
  [find-security-bug](../find-security-bug/SKILL.md)
- 本技能接走 `Q-xx` / `S-xx` 或现场堆栈，负责落地

手法细则见 [references/debug-playbook.md](references/debug-playbook.md)。
交付结构见 [finding-schema.md](../_shared/finding-schema.md) 的修复记录模板。
证据纪律见 [evidence.md](../_shared/evidence.md)。
完整示范见 [examples/scenario.md](examples/scenario.md)。

## 铁律

1. **先复现后动手。** 没有失败信号（测试、堆栈、确定步骤）就还在调查，
   不许提交「也许能好」的改动。
2. **一次一个假说。** 单变量实验；证伪就换假说，不叠补丁。
3. **最小修复。** 只改根因对应的不变量；重构、风格、无关优化写进「故意不改」。
4. **验证是完成条件。** 原复现必须从失败变通过；跑不了测试要在记录里写残留风险，
   不能把「应该好了」当成完成。
5. **安全补丁不用利用脚本验证。** 用合法/非法输入的回归证明控制已关上。

## 执行步骤

### 1. 接住问题

把输入归一成一条问题陈述：

- 有 `Q-xx` / `S-xx`：把该条当作待证假说，先复现它，不要把发现报告当成已证实；
- 只有堆栈或「它坏了」：补一句话问题 + 失败信号，等价于临时发现；
- 用户其实还在「帮我看看有没有问题」：转回对应的 find-* 技能。

复现写不出来 → 停在调查，向用户要日志、输入、或允许加一条失败测试。

### 2. 调查与假说

按 playbook 第 1–3 段走：读完整错误 → 隔离层 → 从坏值回追 → 对照正常路径 →
提出一个具体假说并做单变量实验。

连续两个假说被证伪：回到调查，不要开始霰弹改文件。
三次针对同一根因的补丁仍失败：停止叠加，写入未覆盖风险；
若像结构问题，建议 `engineering-design`，而不是第四块创可贴。

### 3. 修复

红灯（失败复现）在先，产品代码在后。diff 只包含根因所需的行。
安全条目还要关上报告里那条数据流或授权缺口，并补回归：
合法用户仍能访问自己的资源，非法 ID / 未授权角色被拒。

### 4. 交付

按修复记录模板输出，然后才改代码（或边改边填，但用户看到的完成态必须四段齐全）。
新发现的无关缺陷只记转交，不顺手改。

## 特殊情况速查

| 信号                               | 处置                                                                   | 条目 |
| ---------------------------------- | ---------------------------------------------------------------------- | ---- |
| 还没有失败信号，用户要「先扫一遍」 | 转 find-bug / find-security-bug                                        | E1   |
| 发现条目标「存疑」且复现失败       | 回写排除原因，不修想象中的缺陷                                         | E2   |
| 修一处引出无关缺陷                 | 记转交，本轮不顺手改                                                   | E3   |
| 用户催「先改了再查」               | 拒绝跳过调查；可以先加失败测试把红灯钉住                               | E4   |
| 安全修复被要求附 exploit           | 拒绝；用回归测试证明控制已关上                                         | E5   |
| 三次补丁仍失败                     | 停手，写未覆盖风险，评估是否结构问题                                   | E6   |
| 根因在上游依赖                     | 记录版本与上游 issue；本仓库只做防御性校验或锁定，不改 vendor 源码充数 | E7   |

## 自检

- [ ] 修复记录里有可核对的复现与假说实验
- [ ] 产品代码改动与根因一一对应，没有顺手重构
- [ ] 原复现已通过，或明确写出为何无法跑以及残留风险
- [ ] 没有用吞异常、放宽类型、删除断言来「变绿」
- [ ] 安全修复没有附带利用脚本，回归覆盖合法与非法路径
