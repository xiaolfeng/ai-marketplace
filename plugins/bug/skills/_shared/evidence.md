# 证据纪律

配合 [finding-schema.md](./finding-schema.md) 使用：模板管结构，本手册管
「这句话算不算数」。三份技能共用；安全审查额外遵守文末「安全取证」一节。

## 三级证据

| 级  | 什么算                                         | 能支撑的置信度 | 典型来源                                         |
| --- | ---------------------------------------------- | -------------- | ------------------------------------------------ |
| 一  | 失败测试、可运行复现、异常堆栈精确落到行       | 确定           | 测试输出、用户提供的日志、本轮亲自跑通的最小用例 |
| 二  | 完整源 → 汇数据流，且路径在现有分支条件下可达  | 倾向           | 源码追踪、调用图、配置默认值证明路径会走到       |
| 三  | 局部反模式或缺失检查，但入口、消毒或授权未追完 | 存疑           | 模式匹配、linter 同类信号、单函数阅读            |

升级只靠新证据，不靠把「可能」改成「显然」。二级不能写成确定——没跑过的
数据流分析是不健全的，这是静态分析的固有上限，不是谦虚。

## 一条发现必须同时有的四件

1. **位置**：仓库内路径 + 行号（或稳定符号名）。没有位置的条目直接删。
2. **机制**：坏值 / 坏请求从哪进来、在哪变成错的、现有检查为何没拦住。
3. **影响**：具体调用方或角色会怎样；写不出「谁受害」就降严重度。
4. **反证**：这条不成立的最强理由。想不出反证本身就是信号——多半还没看全。

缺任何一件，条目最多标「存疑」，或移入「排除 / 覆盖缺口」。

## 数据流怎么写

安全与质量都用同一句式，避免「看起来像注入」这种空判断：

```
源：<不可信入口或内部坏值产生点>
路径：<中间函数，注明有无分支/消毒>
汇：<错误被观察的点：错误结果 / 崩溃 / SQL / 文件 / 授权决定>
消毒或授权：<有 / 无 / 不完整，指出具体检查>
```

源或汇任缺，就不是二级证据。

## 不算证据的话

- 「这段写得不好 / 不够优雅 / 不符合最佳实践」——风格，不是缺陷；
- 「可能会有问题」而不指出机制——猜测；
- 「网上说这种写法常有漏洞」而无本仓库路径——外援口碑，当线索不当发现；
- 工具扫描器的规则名本身（Semgrep 规则 ID、ESLint 规则）——只是线索，
  要再走一遍数据流才进清单；
- 生成代码、锁文件、第三方实现里的问题，却写成本项目的发现——标清归属，
  否则算张冠李戴。

## 安全取证（find-security-bug 强制，fix-bug 修安全缺陷时同样适用）

1. **授权范围先于分析。** 默认只读用户指定的本仓库路径；未声明的远程主机、
   生产环境、他人系统一律不碰。
2. **取证不等于利用。** 报告写输入类别与被绕过的检查
   （「`userId` 取自查询参数且未与会话比对」），不写可直接打的 payload、
   exploit、武器化 PoC、或可复制的攻击命令。
3. **身份模型必须出现。** 每条安全发现写清攻击者要什么身份、要不要跨用户。
   写不出身份就降为存疑。
4. **质量问题不要灌成漏洞。** 空指针、竞态、资源泄漏默认走 `find-bug`；
   只有当它跨越安全边界（未授权可打崩共享服务、可造成机密泄露）才升格，
   并在条目里写明升格理由。

## 与修复的衔接

`fix-bug` 把发现清单里的条目当作**待证假说**，不是已证实的事实：
先复现（或写出失败测试），再动手。发现侧标「存疑」的条目，复现失败就回写
排除原因，不要用补丁去「预防一种没发生过的想象」。
