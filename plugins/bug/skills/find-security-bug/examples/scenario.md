# 示范场景 —— 授权范围内的 IDOR，报告里没有 payload

展示 `find-security-bug` 的标准形态：钉身份模型、写数据流、类别用
OWASP:2025，建议方向只指出缺失的检查。代码与接口均为虚构。

## 输入·用户的原始请求

> 对我们仓库里的订单 API 做一次安全审查，重点看看会不会越权。
> 不要打生产，本地也别真去刷别人的订单。

## 第 1 步 · 钉范围

资产：`services/order-api/` 的 HTTP handler。信任边界：匿名 / 已登录用户 /
其他用户。授权：仅静态阅读本仓库，不对任何主机发请求。

## 第 2–3 步 · 取证（节选）

`GET /orders/:id` 用路径参数加载订单，未见与 `session.userId` 比对。
匿名路由挂了鉴权中间件；管理接口 `POST /orders/:id/refund` 检查了 `role=admin`。
`search` 把查询字符串拼进 SQL——源是查询参数、汇是 `Query`，中间无参数化。

## 第 4 步 · 报告交付

> ## 范围
> - 目标：`services/order-api/` HTTP API
> - 口径：安全（静态阅读，无动态探测）
> - 假设：会话里的 `userId` 是唯一可信身份；租户字段本轮未出现
> - 未看：前端仓库、网关配置、生产环境
>
> ## 发现清单
>
> ### S-01. 已登录用户可按订单 ID 读取他人订单
> - 类别：A01:2025 Broken Access Control（CWE-862 Missing Authorization）
> - 严重度：高
> - 置信度：倾向
> - 位置：`services/order-api/handler.go:77-91`（`GetOrder`）
> - 证据：二级。源 = 路径参数 `id`；路径 = `repo.FindByID` 后直接序列化；
>   汇 = 响应正文中的地址与金额；消毒/授权 = 仅有「已登录」检查，
>   未见 `order.UserID == session.UserID`
> - 身份模型：任意已登录用户，跨用户
> - 影响：知道或枚举订单 ID 即可读取他人收货信息
> - 为何成立：对象级授权缺失
> - 为何可能不成立：若网关在仓库外按 ACL 过滤（本仓库未见）
> - 建议方向：在加载后用会话身份约束对象归属；列表接口同样按归属过滤
>
> ### S-02. 订单搜索把不可信输入拼进 SQL
> - 类别：A05:2025 Injection（CWE-89 SQL Injection）
> - 严重度：高
> - 置信度：倾向
> - 位置：`services/order-api/search.go:33-40`（`Search`）
> - 证据：二级。源 = 查询参数 `q`；路径 = 字符串拼接后交给 `db.Query`；
>   汇 = SQL 执行；未见参数化或白名单
> - 身份模型：已登录用户（该路由挂了登录中间件）
> - 影响：查询入口可改变 SQL 语义，读取范围取决于当前数据库账号权限
> - 为何成立：汇是查询执行，中间没有参数绑定
> - 为何可能不成立：驱动若另有预处理（本文件未见）
> - 建议方向：改成参数化查询；不要在报告或测试里放利用字符串
>
> ## 转交
> - `GetOrder` 在订单不存在时返回未包装的空指针（`handler.go:84`）→ `find-bug` C1
>
> ## 排除
> - `POST /orders/:id/refund`：有 `role=admin` 检查，本轮未发现垂直越权
>
> ## 覆盖缺口
> 未做动态测试、未跑 SCA、未审查网关；S-01/S-02 均为静态数据流，置信度到不了「确定」。

## 复盘要点

- 身份模型写在每条发现里，而不是只在开头提一句「注意越权」；
- 建议方向是「补对象级授权 / 参数化」，没有出现具体利用串；
- 空指针被转交而不是冒充漏洞。
