# 示范场景 —— 从「看看构建工具」到一份收窄得当的调研报告

展示 `research-normal` 全流程的标准形态：三问立项怎么补齐、粗筛如何收窄候选、
冲突信息怎么并列呈现、「只述不做」在结尾长什么样。人名、公司与数据均为虚构。

## 背景

【输入·用户的原始请求】

> 我们后端这边仓库越拆越散，十几个 Git 仓互相依赖改一次要连发好多服务，
> 领导让我看看 monorepo 这条路。你帮我调研一下？

## 第 1 步 · 立项：补齐三要素

【输出·AI】

```
开工前确认三件事：
① 问题——你关心的是「monorepo 值不值得迁」本身，还是假定要迁、只差选工具？
② 候选——有没有已经看中的方案？（pnpm workspace / Turborepo / Nx / Bazel 等）
③ 产出——给领导汇报用的话，对比表 + 结论速览的形式够吗？
```

【输入·用户】
> 值不值我们其实内部倾向过了，就是要迁，卡在用什么工具。领导要看个对比表。
> 我就知道个 pnpm workspace 和网上老被吹的 turbo，其他随便你们。

## 第 2 步 · 粗筛收窄（速查表 E4 示范）

初步候选池：`pnpm workspace`（包管理自带编排）、`Turborepo`、`Nx`、`Bazel`。

浅层快查后的收窄结论：

| 候选 | 一轮判断 | 处置 |
| --- | --- | --- |
| pnpm workspace | 编排能力弱，但作为包管理基座与所有其他候选兼容 | **保留作基座**，不单独参选 |
| Turborepo | 与 pnpm 深度兼容，学习曲线缓 | 进入深查 |
| Nx | 功能最全，生态插件丰富 | 进入深查 |
| Bazel | 构建正确性强但规则体系学习成本陡峭，团队无 Java/Bazel 背景 | 排除，理由入档 |

向用户同步收窄结果并获认可 → 深查对象锁定 **Turborepo vs Nx**。

## 第 3 步 · 分维度收集（节选关键证据）

- **功能匹配**：两者均支持任务图增量构建；Nx 多出受影响范围检测与代码生成器（来源①③）；
- **性能与规模**：Turborepo 官方宣称远端缓存带来数量级提速——注意这是**宣称作**；
  第三方在百仓库级做的复测显示收益集中在 CI 场景（来源④⑤，「存疑」级）；
- **运维成本**：Turborepo 配置面极小（约定优于配置）；Nx 的 nx.json 与生成器需要专人维护（来源①②）；
- **社区与生态**：均为 MIT 许可；框架适配插件 Nx 显著更多（来源③⑥）；双方版本行为均以最新大版本为准；
- **团队迁移成本**：pnpm workspace 现有目录结构可直接映射进两者（来源⑦）；
  ⚠️ 仅单篇经验帖提及 Nx 迁移脚本对非标准 layouts 有坑——**单源，标「存疑」**（来源⑧）。

已排除清单（节选）：某内容农场「彻底告别构建慢」一文（无原始数据、同文多站转载）；
某 2023 年的对比测评（其所测大版本均已 EOL，按时效规则不采信结论，仅留线索）。

## 第 4 步 · 对比矩阵

| 维度 | Turborepo | Nx |
| --- | --- | --- |
| 任务编排 | 任务图 + 远端缓存（①） | 任务图 + 分布式缓存 + 受影响检测（③） |
| 上手成本 | 约定式配置，几乎零文件（①） | nx.json + 插件体系，需维护人（②） |
| 生态插件 | 聚焦 JS/TS 栈（⑥） | 多语言/多框架适配广（③） |
| 性能宣称 | 官方宣称数量级提升（④·宣称） | 官方宣称分布式缓存高命中（③·宣称） |
| 第三方实测 | CI 场景收益集中，本地中仓库差距小（⑤·存疑） | 同左，样本更少 |

## 复盘要点

- **粗筛建功在「排除有理由」**：Bazel 出局的理由写进了档案，三周后如果有人再提它，一句「团队无此技术栈储备」就能接住；
- **宣称作与实测评全程分家**：官方性能页里的夸张数字没有进入任何结论句，只在矩阵里挂着「宣称」标签；
- **单源信息不沉默也不升格**：来源⑧照常呈现帮读者建立视野，但「存疑」标签焊死在身上；
- **结尾没有出现「建议选用 X」**：考虑点把分岔条件摆平后交还决策——拍板属于领导的会议室，或未来的 RFC。
