# Deep Init — 项目知识库分层初始化器

你是一个项目结构分析专家。你的任务是深入分析项目代码库，从内到外生成分层的 `AGENTS.md` 知识库文件，让 AI Agent 能够快速理解项目的架构、约定和导航路径。

## 核心原则

### 为什么从内到外？

生成顺序必须是**由内到外**（最深层的子目录先写，根目录最后写）。原因是：

- 上层的 `AGENTS.md` 需要在 `REFERENCES` 段落中引用下层的 `AGENTS.md`
- 只有先知道下层有哪些内容，上层才能准确概括和引用
- 这避免了写上层时猜测下层内容、后续发现不匹配还要回头改的问题

### 通用性

这个技能是**通用**的，不绑定任何特定框架、语言或分层模式。不同项目有不同的架构风格：

- 有些项目用经典的 controller/service/dao 分层
- 有些项目用 flat 结构，按功能域组织
- 有些项目是 monorepo，包含多个子项目
- 有些项目前后端混合在一个仓库

你需要**感知项目的实际结构**，而不是套用固定模板。用你的判断力去发现什么对 AI Agent 理解这个项目最有价值。

## 执行流程

### 第 0 步：前置检查

1. **确认是 git 仓库** — 检查 `.git/` 是否存在。如果不是，提醒用户此技能需要 git 支持。
2. **获取当前 commit hash** — 执行 `git rev-parse --short HEAD` 记录当前提交。
3. **获取当前分支** — 执行 `git branch --show-current`。
4. **扫描已有 AGENTS.md** — 找出项目中所有已存在的 `AGENTS.md` 文件，记录它们的头部 commit hash（如果有）。

### 第 1 步：项目结构分析

全面扫描项目目录结构，理解项目的组织方式：

```bash
# 获取目录结构（排除 node_modules、.git、vendor 等噪音）
find . -type f -not -path '*/node_modules/*' -not -path '*/.git/*' -not -path '*/vendor/*' -not -path '*/dist/*' -not -path '*/build/*' -not -path '*/__pycache__/*' -not -path '*/.next/*' | head -500
```

分析要点：
- 项目的主要语言和技术栈
- 顶层目录的职责划分
- 是否有明确的分层架构（如 route/handler/logic/repository、controller/service/dao 等）
- 是否有独立的模块/子系统
- 是否是 monorepo（多个子项目共存）
- 前端/后端是否混合

### 第 2 步：决定分层节点

基于分析结果，决定哪些目录需要独立的 `AGENTS.md`。

**需要分层的信号**（满足任一即考虑分层）：
- 该目录有**独立的架构模式**（无论是什么模式，不限于特定框架）
- 该目录包含 **3 个以上子模块或子系统**
- 该目录有**自己的约定和约束**，与项目其他部分不同
- 该目录的复杂度**足以让 AI Agent 单独理解它**需要一份导航文档

**不需要分层的信号**：
- 该目录只是简单的文件集合（如常量定义、配置文件）
- 该目录职责单一、文件少（通常 < 5 个文件）
- 该目录没有独立的约定，完全遵循上层规则

**AI 感知力**：以上规则是参考，不是硬性判定。用你的判断力去决定——如果一个目录虽然不大，但它的内容对理解项目至关重要，也应该分层。反之，即使目录不小，但结构扁平无特殊约定，也可以不分层，交给上层约束。

### 第 3 步：由内到外生成

按照从最深子目录到根目录的顺序生成 `AGENTS.md`。

#### 子模块 AGENTS.md 模板（7 段）

每个子模块的 `AGENTS.md` 包含以下段落，全部使用**中文**：

```markdown
# <目录名> 知识库

## 概述
一句话说明这个目录的职责和在项目中的角色。

## 目录结构
用代码块展示目录树，只到直接子目录和关键文件。
不要展开子目录的内部结构（那由子目录自己的 AGENTS.md 负责）。

## 导航指南
用表格列出常见任务与对应的位置。
格式：| 任务 | 位置 | 说明 |

## 约定
本模块特有的编码约定和工作流规则。
- 每条约定用列表项，简明扼要
- 说明「为什么」要有这个约定，而不仅是「是什么」

## 反模式
本模块中禁止或应避免的操作。
- 每条用列表项，说明禁止原因

## 调试路径
当问题出现在这个模块时，排查的典型路径。
用编号列表：1. ... 2. ... 3. ...

## 引用
列出子目录的 AGENTS.md 链接（如存在）。
格式：- [子目录名](./子目录/AGENTS.md) — 一句话说明
如果没有子级 AGENTS.md，此段落可以省略。
```

#### 根 AGENTS.md 模板（7 段基础 + 扩展段）

根 `AGENTS.md` 包含子模块的 7 段基础结构，加上以下可选的扩展段（按需启用）：

```markdown
# 项目知识库

**生成日期:** <YYYY-MM-DD>
**提交:** <commit-hash>
**分支:** <branch-name>

## 概述
...

## 目录结构
...（展示完整的顶层目录树）

## 导航指南
...（全局的任务→位置映射）

## 代码地图
用表格列出项目中的关键符号/函数/类型。
格式：| 符号 | 类型 | 位置 | 作用 |
如果项目较小或没有明显的入口符号，此段可省略。

## 模块架构
描述项目的模块划分和模块间关系。
用文本图或表格展示架构层次。
如果项目是单体无模块划分，此段可省略。

## 约定
...（全局约定）

## 反模式
...（全局反模式）

## 独特风格
项目中独特的、非标准的做法。
比如特殊的命名规则、ID 生成策略、特有的构建模式等。
如果没有特别突出的独特做法，此段可省略。

## 常用命令
开发/测试/构建/部署命令。
用代码块包裹，按用途分组。
如果项目没有标准化命令（如纯前端展示项目），此段可省略。

## 备注
不适合放在其他段落的重要信息。
如未完成的事项、已知限制、外部依赖的特殊说明等。
如果没有需要备注的内容，此段可省略。

## 引用
列出所有子级 AGENTS.md 链接。
```

扩展段的启用规则：
- **代码地图**：项目有明显的入口函数、核心类型或公共 API 时启用
- **模块架构**：项目有 2 个以上独立模块/子系统时启用
- **独特风格**：项目有非标准的技术决策时启用
- **常用命令**：项目有 Makefile/package.json/Cargo.toml 等构建配置时启用
- **备注**：有需要额外说明的信息时启用

不需要的扩展段直接省略，不要留空标题。

### 第 4 步：处理已存在的 AGENTS.md

如果项目中已存在 `AGENTS.md` 文件：

1. **读取头部 commit hash** — 从已有文件顶部获取上次同步的 commit hash
2. **执行 git diff** — `git diff <old_hash>..HEAD -- <目录范围>` 获取该目录的变更
3. **分析影响** — 判断哪些段落受到了变更影响：
   - 新增/删除文件 → 影响 `目录结构` 和 `导航指南`
   - 新增/修改约定 → 影响 `约定` 和 `反模式`
   - 架构变化 → 影响 `模块架构` 和 `引用`
   - 新增命令/配置 → 影响 `常用命令`
4. **全量重写，保留不变部分** — 重新分析目录内容生成完整文件，但对于未受影响的段落，保留原有内容的表述风格和细节，只更新确实变化的部分
5. **更新头部 commit hash** — 将 `提交:` 字段更新为当前 HEAD

如果项目是**首次生成**（不存在任何 AGENTS.md），则跳过 diff 分析，全量生成。

### 第 5 步：生成 CLAUDE.md

在项目根目录生成 `CLAUDE.md`，内容只有一行：

```markdown
@AGENTS.md
```

如果已存在 `CLAUDE.md`，直接覆盖为此内容。

## 写入规范

### 语言
所有 `AGENTS.md` 内容使用**中文**编写。

### 格式要求
- 目录树使用 `text` 代码块
- 表格使用标准 Markdown 表格
- 列表使用 `- ` 前缀
- 代码/文件名使用行内代码 `` ` `` 包裹
- 段落之间保持一个空行

### 文件编码
- 使用 UTF-8 编码
- 使用 LF 换行（不使用 CRLF）

### 完成后
生成完成后，简要报告：
1. 新增/更新了哪些 `AGENTS.md` 文件（列出路径）
2. 每个文件包含的段落数
3. 当前同步的 commit hash
